\begin{abstract}
After login, a web application recognises a user only by a session identifier,
so an attacker who steals it can act inside the session without any failed
login. Binding the session to the client's IP address is a common defence, but
honest users also change networks, which causes false alarms. In this project we
built SICA (Session Integrity and Continuity Analysis), a simple rule/risk-based
detector that uses only web server access-log information and no machine
learning. SICA compares each request's client (IP address, /24 and /16 network,
browser, version, operating system and device) with the client the session
belongs to, and scores User-Agent changes, graded network changes and binding
forks, where an earlier client returns after a different one, as happens when a
victim and an attacker share a session. A fixed weighted sum gives a risk score,
and a fixed threshold decides ALLOW or ALERT. On 100-session samples of two
public access logs, each with 20 simulated hijacks, SICA detected 15 and 13
hijacks with no false alarm on the 80 normal sessions, and it passed all 8
deterministic test cases. Hijacks where the victim never returns and the
attacker copies the User-Agent were missed.
\end{abstract}

\begin{IEEEkeywords}
session hijacking, web access logs, client binding, rule-based detection
\end{IEEEkeywords}

\section{Introduction}
% =====================================================================

HTTP is stateless, so a web application keeps a user logged in by giving the
browser a session identifier after authentication, normally in a
cookie~\cite{rfc6265}. From then on the identifier is the only proof of identity
the server checks. Whoever presents it is treated as the user. Attackers can
obtain it through cross-site scripting, network interception, malware or leaked
logs, and measurements on popular services have shown that stolen session
cookies can expose private user data in
practice~\cite{sivakorn2016cookie,calzavara2017surviving}.

Detecting a stolen session after login is difficult. The attacker never
authenticates, so there is no wrong password to notice, and each request carries
a valid identifier with content that can look exactly like the victim's. The
only evidence lies in the context: which network the requests come from, which
client software sends them, and how this changes during the session.

The usual server-side rule is to bind the session to the client's IP address and
end it when the address changes. The main problem is that legitimate users also
change addresses. Dynamic addresses are renumbered~\cite{padmanabhan2016dynamic},
and a phone may move from Wi-Fi to a mobile network in the middle of a session.
An IP pin treats each of these as an attack. Since real hijacks are rare
compared with normal sessions, even a few percent of false alarms means that
most alerts are false~\cite{axelsson2000baserate}. A richer client binding helps
here. A new host in the same /24 network is weak evidence, while a jump to a
different network, or a switch to a different browser or operating system, is
much stronger.

Previous work has approached session theft from several directions. Some
defences make a stolen token useless, for example by replacing the static cookie
with per-request tokens, which needs support in both browser and
server~\cite{dacosta2012onetime}. A survey of web session security notes that
most proposed defences work in the browser, in the protocol or in the
application code~\cite{calzavara2017surviving}. SHPF binds the session to a
browser fingerprint collected with JavaScript and ends the session when the
fingerprint changes~\cite{unger2013shpf}. Risk-based authentication compares the
IP address and User-Agent of a login with the user's login
history~\cite{freeman2016whoareyou}. Log-based detectors learn models of web
request parameters~\cite{kruegel2003anomaly} or of system log sequences with deep
learning~\cite{du2017deeplog}. These studies show that client context is a
useful security signal, but they need client changes or JavaScript, work only at
login time with per-user history, or depend on trained models of request
content.

Our project looks at a narrower, practical question: \emph{can a server flag
observable mid-session hijacking using only the access-log information it
already writes, with a rule that is easy to explain?} Our answer is SICA. It is
based on one observation about the shape of client changes. A user who moves
from client $A$ to client $B$ leaves $A$ behind ($A\,A\,A\,B\,B\,B$). When an
attacker uses a stolen session while the victim is still browsing, the two
clients alternate and the earlier client comes back ($A\,A\,B\,A\,B$). We call
this return a \emph{binding fork}.

\textbf{Objective.} The objective of this course project is to detect possible
mid-session HTTP session hijacking using server access-log information and a
rule/risk-based client-binding approach: three simple checks, fixed weights and
one fixed threshold, implemented in plain Python, and demonstrated on two public
log samples with simulated hijacks and on deterministic test cases.

\section{Methodology}
% =====================================================================

\subsection{Problem Definition}

A web server logs each request with the client IP address, time, requested path
and User-Agent string. A session is the ordered list of requests that present
the same session identifier. For every session, SICA must decide ALLOW or ALERT
from this information alone. We consider two kinds of hijack: a \emph{silent
takeover}, where the victim stops sending requests after the theft, and a
\emph{concurrent hijack}, where the victim and the attacker both keep using the
session.

\subsection{Client Binding}

Each request is mapped to a client binding with seven fields:
\begin{center}
IP address \;|\; /24 \;|\; /16 \;|\; browser \;|\; version \;|\; OS \;|\; device
\end{center}
The first three fields form the \emph{network part}, and the last four, parsed
from the User-Agent string with fixed text rules, form the \emph{agent part}. A
new host in the same /24 is typical of an address renewal. A new /24 inside the
same /16 often means another access network of the same provider. A new /16
usually means the client has left the network where the session started. On the
agent side, a version change can follow a browser update, but a real client
does not switch to a different browser, operating system or device class in the
middle of a session.

For each session, SICA keeps a \emph{reference client}, the last client, and a
list of the last four distinct clients. When a client makes a one-way move to a
new client binding, the reference moves with it, so a user who settles on a new
network is counted only once. When an earlier client returns, the reference is
left unchanged, because with two clients alternating there is no way to tell
which one is the owner.

\subsection{The Three Checks}

\textbf{User-Agent change ($U$).} It compares the agent part of the request with
the reference. It is 1.00 if the browser family, operating system or device
class changed, 0.35 if only the major browser version changed, and 0 otherwise.

\textbf{Network change ($N$).} It measures how far the client moved in the
network hierarchy relative to the reference:
\begin{center}
\small
\begin{tabular}{@{}lc@{}}
\toprule
Change relative to the reference & $N$ \\
\midrule
new /16 network & 1.00 \\
new /24 inside the same /16 & 0.45 \\
new host inside the same /24 & 0.15 \\
same IP address & 0 \\
\bottomrule
\end{tabular}
\end{center}
The value is graded instead of a simple ``changed or not changed''. This is the
main difference from an IP pin: a small move inside the same network costs
little, while leaving the /16 network costs the full value.

\textbf{Old client back, the binding fork ($F$).} It does not look at the size
of a change but at its shape. It is 1.00 when the client of the current request
differs from the previous request's client but is already in the list of recent
clients:
\begin{center}
\begin{tabular}{@{}l@{\quad}l@{}}
Legitimate move: & \texttt{A A A A B B B B}\\
Concurrent hijack: & \texttt{A A A B A B A}
\end{tabular}
\end{center}
In the first session, $B$ is new, so $F$ stays 0. In the second, $A$ returns
after $B$ has appeared. A single client that moves once does not produce this
pattern, while two clients sharing one session cannot avoid it. The fork is
therefore a strong sign that two clients use the same session, although it does
not prove an attack.

\subsection{Risk Score and Threshold}

The three values are combined into a risk score for every request:
\begin{equation}
R = 0.3718\,U + 0.3301\,N + 0.2981\,F ,
\end{equation}
and the first request of a session has $R=0$. The weights are fixed constants
that add up to one; they were derived once from attack-free W1 sessions, where a
check that rarely fires on normal traffic received a larger weight. The session
decision uses its peak risk $R_{\max}$:
\begin{center}
$R_{\max}\ge 0.6282 \Rightarrow$ ALERT, \qquad $R_{\max}< 0.6282 \Rightarrow$ ALLOW.
\end{center}
The threshold equals the network weight plus the fork weight. A network change
alone (0.3301) or a User-Agent change alone (0.3718) stays below it, while a
network and User-Agent change together (0.7019) or an old client returning from
another network (0.6282) reaches it. Nothing is learned per user or per dataset.

\subsection{Overall Workflow}

Fig.~\ref{fig:arch} shows the complete pipeline, from the access log to the
final decision. The whole detector is one plain Python file (\texttt{run.py})
using only the standard library, with constant work per request.

\begin{figure}[t]
\centering
\input{figures/report_architecture}
\caption{SICA workflow. Each request becomes a client binding, three checks
compare it with the session's reference and recent clients, the weighted sum
gives the risk, and the session's peak risk is compared with the fixed
threshold 0.6282.}
\label{fig:arch}
\end{figure}

\textbf{Architecture blocks.} The workflow in Fig.~\ref{fig:arch} runs as follows.
\begin{enumerate}
\item \emph{Access logs.} Requests with session ID, IP address and User-Agent.
\item \emph{Track session.} Requests are grouped by session ID in arrival order;
the session keeps its reference client, last client and last four clients.
\item \emph{Client binding.} Each request is converted into the seven-field
binding described above.
\item \emph{Checks.} $U$, $N$ and $F$ compare the binding with the reference and
with the recent clients.
\item \emph{Risk score.} The values form the weighted risk $R$, and the session
keeps its highest value $R_{\max}$.
\item \emph{Decision.} $R_{\max}$ is compared with 0.6282: ALLOW or ALERT.
\end{enumerate}
In the manual mode of the program, every request also prints which changes
were found, so each alert can be explained.

\subsection{Worked Example}

Table~\ref{tab:example} traces two short sessions. Client $A$ and client $B$
have the same browser but lie in different /16 networks, so $U=0$ throughout.

\begin{table}[t]
\centering
\caption{Worked example with the weights and threshold used in \texttt{run.py}.}
\label{tab:example}
\footnotesize
\setlength{\tabcolsep}{3.6pt}
\begin{tabular}{@{}lcccccccc@{}}
\toprule
Request $t$ & 1 & 2 & 3 & 4 & 5 & 6 & $R_{\max}$ & Decision \\
\midrule
Legitimate & A & A & A & B & B & B & & \\
\quad risk $R_t$ & 0 & 0 & 0 & 0.3301 & 0 & 0 & 0.3301 & ALLOW \\
\midrule
Hijack & A & A & B & A & B & & & \\
\quad risk $R_t$ & 0 & 0 & 0.3301 & \textbf{0.6282} & 0.2981 & & 0.6282 & \textbf{ALERT} \\
\bottomrule
\end{tabular}
\end{table}

In the legitimate session, request 4 moves to a new /16, so $N=1$ and
$R=0.3301$. The reference then moves to $B$, and the remaining requests score 0.
The peak stays below the threshold and the session is allowed. In the hijacked
session, request 3 looks exactly like that same move. At request 4, however,
the victim's client $A$ returns while it is still in the recent list, so $F=1$,
and the /16 has changed again relative to the reference $B$, so $N=1$. The risk
becomes $0.3301+0.2981=0.6282$, which reaches the threshold, and the session is
alerted.

\subsection{Legitimate Mobility versus Hijacking}

SICA separates the two cases by the shape of the change. A one-way move, such as
a new address or a browser update, is charged once, after which the reference
follows the user. A concurrent hijack brings an earlier client back, which
triggers $F$ and, when the networks differ, $N$ as well. Two cases remain hard.
A device that keeps switching between two networks (interface flapping) also
alternates and would be alerted. A silent takeover with a copied User-Agent
produces the same log as a one-way move, so SICA allows it.

\section{Results}
% =====================================================================

\subsection{Experimental Setup}

We used two public sample logs from the Elastic Examples repository. W1 is an
Apache log of a personal technical website (10,000 requests); W2 is an Nginx
demonstration log (51,462 requests), mostly from Debian and Ubuntu package
clients (APT). The logs contain no session cookies, so we rebuilt sessions with
project-specific rules: requests with the same IP address and User-Agent, a new
session after a pause of more than 30 minutes, and at least 7 requests. The
first 100 sessions of each log form the samples used by SICA: 1,485 requests
for W1 and 1,395 for W2. Each sample is a CSV file with one row per request and
the structured fields \texttt{session\_id}, \texttt{request\_no},
\texttt{timestamp}, \texttt{ip\_address}, \texttt{browser},
\texttt{browser\_version}, \texttt{operating\_system},
\texttt{device\_type} and \texttt{attack}; the four browser fields are parsed
from the User-Agent string, and a session keeps all of its requests in order.

The logs contain no confirmed real attacks, so the hijacks are \emph{simulated}.
Every fifth session (20 per dataset) received attacker requests at its middle,
sent from the IP address of another session in a different /16 network. Four
types rotate, five sessions each: concurrent (two attacker requests, the victim
keeps browsing) and takeover (the attacker replaces the second half), each with
the attacker's own User-Agent or a copy of the victim's. The other 80 sessions
are unchanged real traffic. In addition, 8 hand-made deterministic test cases
(Table~\ref{tab:tests}) each store an expected decision.

No normal session was alerted: every normal session in both samples kept one
client from start to end and scored a peak risk of 0. All 10 concurrent hijacks
per dataset were detected. Takeovers with the attacker's own User-Agent were
detected in 5 of 5 cases on W1 and 3 of 5 on W2, where two attackers used an APT
client that differed from the victim's only in version ($0.1301+0.3301=0.4602$).
All 10 takeovers with a copied User-Agent were missed with risk 0.3301, exactly
the score of a legitimate network change. All 8 test cases produced their
expected decision.

\subsection{What SICA Detects and Misses}

SICA is strongest when two clients share a session: the victim's return creates
a binding fork, and the alert fires as soon as that happens, whether or not the
attacker copies the User-Agent. A change of network and User-Agent at the same
time is also alerted. A single change of network or of User-Agent alone is
allowed on purpose, because honest users produce such changes. An attacker who
takes over completely and copies the User-Agent is therefore missed, and an
attacker with the victim's exact IP address and User-Agent cannot be seen in
these fields at all.

\textbf{Limitations.} The attacks are simulated rather than captured from real
incidents, and the samples are small (100 sessions each, rebuilt from IP and
User-Agent rather than real cookies), so the normal sessions contain no
legitimate client changes and the zero false-alarm result is optimistic. The
weights and the threshold are fixed and not tuned per site. SICA sees only
log fields: no packets, cookies or page content. Legitimate network changes and
interface flapping can look like the patterns above.

% =====================================================================
\section{Conclusion}
% =====================================================================

In this project we built SICA, a lightweight rule/risk-based detector that looks
for mid-session HTTP session hijacking using only the web server's access-log
information. SICA describes each request by a client binding, scores User-Agent
changes, graded network changes and the binding fork, and compares the
session's peak risk with a fixed threshold of 0.6282. The final implementation
is a single plain Python file without machine learning. On the W1 and W2
samples it detected 15 and 13 of 20 simulated hijacks with no false alarm, and
it passed all 8 test cases. The project showed that log-only detection is
practical for one clear case: two clients using the same session, one of which
returns. Silent takeovers with a copied User-Agent remain indistinguishable
from normal mobility. Future work can use larger real logs with real session
cookies and legitimate client changes while keeping the design simple and
explainable.
